# Sign-up address and phone, real Mumbai store addresses (design)

Date: 2026-10-05. Branch `signup-address-geocoding`. Requested by Vishal after the order #1e2b768d showed "12579 km from your address": the demo delivery partner's stored position was in New Jersey, and the stores carry placeholder addresses with rough coordinates.

## Decisions (Vishal, 2026-10-05)
- Customer sign-up on the website AND the phone app asks for full name, email, password, phone and address; all are stored in the database.
- The registration address is geocoded on the SERVER with a new server-side Google key (`GOOGLE_MAPS_SERVER_API_KEY` in the root `.env.local`, Geocoding API only, created by Vishal). It becomes the customer's saved delivery location (the existing `users.saved_lat/saved_lng/saved_label`); the customer can change it later in the location picker.
- All 77 stores get a real Mumbai street address, geocoded through the same server key so the coordinates come from Google, not from memory.
- The 4 delivery partners are moved to Mumbai, then "Reset Data" is run last (it also deletes Vishal's own order).

## Sign-up (web + phone, one server rule)
- `POST /api/auth/signup` additionally requires `phone` (10-digit Indian mobile: reuse the checkout phone rule, find it with grep for the recipient-phone validator) and `address` `{line1, line2?, city, state, pincode}` (line1, city, state, pincode non-empty; pincode 6 digits). Existing fields and the 6-character password rule stay. Pure validation goes into `lib/signup-validation.ts` with tests.
- Geocoding happens BEFORE the auth user is created, in a new server-only module (`lib/geocode-server.ts`, `server-only`; pure response parsing in an import-free `lib/geocode-parse.ts` with tests): Google Geocoding API `https://maps.googleapis.com/maps/api/geocode/json?address=...&components=country:IN&region=in&key=...`. Accept only `status OK`, a first result inside India, and a finite lat/lng. No result => 400 "We could not find that address. Check the details and try again." Key missing, quota, network or non-OK/ZERO_RESULTS status other than ZERO_RESULTS => 503 "Address lookup is unavailable right now. Try again later." and NO account is created. Never log the key, the address or the coordinates; never return the key; never echo provider error text.
- After the geocode succeeds: create the auth user, insert `public.users` with `phone`, then insert an `addresses` row for the user (`label` "Home", line1/line2/city/state/pincode, lat, lng, `is_default` true) and set `users.saved_lat/saved_lng/saved_label` (label = short text such as "line1, city", max 200). Any failure after creating the auth user rolls back everything (delete the auth user; cascades delete users/addresses).
- Migration `00000000000034_default_address_unique.sql`: unique partial index on `addresses(user_id)` where `is_default` and `user_id is not null` (one default address per customer).
- The checkout form keeps its "never persisted across sessions" rule; do not prefill checkout from the registration address in this change.
- Web sign-up form (find it under `app/customer/login/page.tsx` or the signup page it uses) and the phone sign-up screen (`mobile/src/app/login/customer.tsx` or the signup screen it links to) get Phone, Address 1, Address 2 (optional), City, State, Pincode fields with inline validation and the server's error messages; no Google calls from the clients.
- Web saved location on the account: the web delivery-location store (`lib/address-store.tsx`, localStorage key `fresh-quick-delivery-location`) must start from the account's saved location for a signed-in customer: after the session resolves, GET `/api/customer/location`; use the server value when localStorage holds no pin (a pin chosen on the web is also PUT to the server, newest local choice wins, failures ignored). The default Mumbai pin stays only for visitors with neither. The phone app already syncs the account location after sign-in.

## Store addresses
- `scripts/data/mumbai-store-addresses.json`: for every one of the 77 stores (key = store name, taken from the database, not invented) a real, specific street address in a Mumbai locality that fits the store's category (spread over the suburbs and south Mumbai; no two stores at the same address): `line1`, `line2` (area/landmark), `pincode` (real for that locality), city "Mumbai", state "Maharashtra". The stores are fictional, so these are real places' addresses.
- `scripts/geocode-stores.mjs` (Node, run by VISHAL because it reads the key from `.env.local`; it must never print the key): geocodes each address with the Geocoding API, requires `status OK`, `partial_match` not true, a location inside the Mumbai bounding box (lat 18.89 to 19.30, lng 72.77 to 73.00) and `location_type` not APPROXIMATE; writes `supabase/data/store-locations.json` (name, line1, line2, pincode, lat, lng, formatted address) and prints a table of passes and failures (never partial output as success; exit code 1 if any store failed, listing them so the data file can be corrected). Resumable: skips stores already resolved in the output file unless `--force`.
- `scripts/apply-store-locations.mjs`: reads `supabase/data/store-locations.json` and updates, per store, `addresses` (line1, line2, city, state, pincode, lat, lng via the store's `address_id`) and `stores.lat/lng`, inside one transaction, idempotent, by default a dry run that prints what it would change; `--apply` writes. Use the same database access approach as the other scripts in `scripts/` (docker exec psql or the service-role client; check what `scripts/seed*` does). Hook it after the seed step of `npm run app:seed` if that script exists, so a reset database ends with real addresses.
- Tests: JSON schema test (77 entries, unique names matching `supabase/seed.sql` store names, unique addresses, pincode 6 digits), pure parser tests, and a stub-server test that runs `geocode-stores.mjs` end to end (project rule: every CLI script needs a run-it test).
