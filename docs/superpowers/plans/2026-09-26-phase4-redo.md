# Phase 4 Redo (Health/Retail/Personal Care/Electronics) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Each of the 16 Health/Retail/Personal Care/Electronics stores
gets a fresh, fully unique 50-item catalog (old shared-20-item-per-store
data from the superseded `.claude/worktrees/marketplace-phase4` worktree
is discarded, not padded — nothing live references it).

**Architecture:** New worktree branched off current `main`. Task 0 ports
the 16 stores' vendor accounts (`auth.users`/`auth.identities`/
`public.users`/`public.addresses`/`public.stores` rows only — never
product rows) from the old worktree's seed files into this worktree's
`supabase/seed.sql`, verbatim. Each of Tasks 1-16 then writes one store's
50 new `insert into public.products` rows from scratch. The shared
append-only registry file (`docs/superpowers/plans/item-name-registry.md`)
tracks every item name used anywhere in the app.

**Tech Stack:** SQL (seed.sql), Pexels Search API via
`scripts/fetch-catalog-images.mjs` for new product photos.

**Spec:** `docs/superpowers/specs/2026-09-26-phase4-redo-design.md`

## Global Constraints

- Old worktree `.claude/worktrees/marketplace-phase4` is never merged and
  never modified by this plan — read-only reference for Task 0's porting
  step.
- Every new item name must be unique across the ENTIRE app — checked
  against `docs/superpowers/plans/item-name-registry.md` (1,276 lines as
  of sub-project B) before it is written, appended to that file in the
  same commit as the SQL that introduces it. Append only, never
  rewrite/restructure the registry.
- `products.price` is a **decimal rupees.paise value** (e.g. `149.75`),
  never integer paise, never x100, for every new item in this plan.
- `is_veg` (`product_attributes: {"is_veg": true|false}`) is set, judged
  on real ingredients, ONLY for Health-category rows that are genuinely
  food-adjacent (protein powder, nutrition bars, supplements, shakes) —
  never keyword-matched. Retail/Personal Care/Electronics rows omit
  `is_veg` entirely (`{}'::jsonb`).
- Each store's 50 new rows must reuse that category's confirmed
  vocabulary from Task 0 exactly — no near-synonym drift.
- Zero schema/migration changes — `category_type` values already exist in
  migration `00000000000020_stores_products_rename.sql`.
- Each store's product count must reach exactly 50 (freshly written, no
  old rows carried over), verified live via
  `count(p.id) ... where store_id = ...`.
- Reuse the existing Pexels-fetch-once pattern (fetch once, bake URLs
  into seed.sql — never called at runtime). Fetched photo must genuinely
  match the item pictured — never a silent fallback to an unrelated
  existing photo (the exact defect sub-project B's final review caught).
- Copy `.env.local` into the new worktree as one of the first setup
  steps, before any task that needs Pexels or runs `npm run build`.

## Review Focus

- A new item name that collides with the registry as it stood before
  this task's own commit (the registry is the authority, not eyeballing).
- A store's final live count landing anywhere but exactly 50.
- A new row's `category` value not matching Task 0's confirmed
  vocabulary for that category exactly.
- `is_veg` present on a non-Health row, or absent/keyword-guessed on a
  genuinely food-adjacent Health row.
- `image_url` silently reusing an unrelated existing product's photo
  because the worktree's Pexels key was unreachable (verify `.env.local`
  presence and a live fetch success before trusting any task's photos).
