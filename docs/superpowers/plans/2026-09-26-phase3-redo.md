# Phase 3 Redo (Grocery/Convenience/Alcohol) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Each of the 12 Grocery/Convenience/Alcohol stores reaches 50+
items (existing 20 kept untouched, 30+ new unique items appended per
store), by appending new rows to `supabase/seed.sql`.

**Architecture:** Pure `supabase/seed.sql` addition per store —
`insert into public.products (...) values (...) on conflict do nothing`
blocks referencing each store's existing `store_id`. No schema change,
no new vendor accounts (all 12 already have owners). The shared
append-only registry file (`docs/superpowers/plans/item-name-registry.md`,
created by sub-project A) tracks every item name used anywhere in the
app so this sub-project never collides with a restaurant dish name or a
name added by a later store in this same plan.

**Tech Stack:** SQL (seed.sql), Pexels Search API via
`scripts/fetch-catalog-images.mjs` for new product photos.

**Spec:** `docs/superpowers/specs/2026-09-26-phase3-redo-design.md`

## Global Constraints

- Existing 20 items per store are NEVER modified, deleted, or reordered
  — pure appends (order_items FK integrity for historical orders).
- Non-base stores' old 20 duplicate-name rows (same names as the base
  store in their category) are also left untouched and NOT renamed —
  grandfathered, out of scope for this plan.
- Every new item name must be unique across the ENTIRE app — checked
  against `docs/superpowers/plans/item-name-registry.md` before it is
  written, and appended to that file in the same commit as the SQL that
  introduces it. Append only, never rewrite/restructure the registry.
- `products.price` is plain rupees, never paise, never x100.
- Each store's new rows must reuse that same store's existing `category`
  vocabulary exactly (grep the store's current rows first) — no
  near-synonym drift (e.g. never introduce "Grocery" next to an existing
  "Staples", or "Alcohol Accessories" next to an existing "Accessories").
- Zero schema/migration changes.
- Each store's product count must reach 50+ (existing 20 + new 30+
  combined), verified live via `count(p.id) ... where store_id = ...`.
- Reuse the existing Pexels-fetch-once pattern (fetch once, bake URLs
  into seed.sql — never called at runtime).

## Review Focus

- A new item name that collides with the registry as it stood before
  this task's own commit (the registry is the authority, not eyeballing).
- Any diff that touches an existing (already-committed) product row
  instead of only adding new ones.
- A store's final live count falling short of 50.
- A new row's `category` value not matching any of that store's existing
  category strings exactly (e.g. "Beverage" vs "Beverages").
- The registry file itself losing an earlier task's entries (append-only
  — a task must never overwrite lines another task added).
